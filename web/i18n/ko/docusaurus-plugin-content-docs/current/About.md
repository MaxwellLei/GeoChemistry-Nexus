**GeoChemistry Nexus**는 매우 긴 기간 동안 유지하기로 한 첫 프로젝트입니다. 적어도 앞으로 5년 동안 계속 업데이트할 계획입니다.

흥미롭게도 처음 이름은 **Geo-Thermometer**였습니다. 처음에는 지질 온도계와 관련된 기초 프로그램만 만들어 계산과 작도를 쉽게 하려 했습니다. 그러나 프로젝트가 진행되고, 특히 작도 모듈이 끝난 뒤, 더 큰 목표를 실현할 수 있다는 것을 알게 되었습니다. 그래서 개념과 기능이 모두 확장되었고, Geo-Thermometer에서 GeoChemistry Nexus로 발전했습니다.

## 이 이름을 쓰는 이유

**GeoChemistry**는 지구화학을 뜻합니다. **Nexus**는 연결점, 허브, 또는 만나는 중심을 뜻합니다.

흩어져 있는 지구화학 계산 방법, 데이터 처리 도구, 광물 화학 분석, 지질 도해 등을 하나의 플랫폼으로 모으려 합니다.

## GeoChemistry Nexus가 필요한 이유

지구화학과 암석학 연구에서 **작도**와 **계산**은 서로 다른 도구에 나뉘어 있는 경우가 많습니다. 데이터 정리는 스프레드시트에, 바탕도 그리기는 범용 벡터 도구에, 온압계 계산은 별도의 스크립트나 오래된 프로그램에 의존합니다. 흐름이 끊기고, 형식이 통일되지 않으며, 재현 비용이 높은 것이 많은 연구자가 일상에서 마주하는 마찰입니다.

한편, 자주 쓰는 판별 도해, 온압계, 관련 계산 도구는 **오랫동안 지속적인 업데이트가 부족한** 경우가 많습니다. 새로 발표된 알고리즘과 고전 모형의 개정이 제때 반영되기 어렵고, 연구자는 몇 년째 멈춰 있는 옛 버전을 그대로 쓰는 일이 많습니다. 더 현실적인 문제는, 연구자가 **직접 개발한** 새 알고리즘이나 도해를 **편리하고 열린 배포 경로 없이** 논문 부록, 개인 스크립트, 좁은 공유에 남겨 두는 경우가 많아, 같은 분야에서 빠르게 퍼지고 다시 쓰이기 어렵다는 점입니다.

![plot_home_ui](/img/about-illustrations/02-research-tool-pain-points.png)

연구 과정에서는 충분히 엄밀하지 않은 방식도 보았습니다. 예를 들어 지질도 바탕도의 형태를 CorelDRAW로 대략 따라 그리는 경우가 있습니다. 눈으로 보면 차이가 크지 않지만, 과학 연구의 관점에서는 엄밀한 과학 정신에 어긋납니다.

그래서 스스로 물었습니다. **왜 도구를 직접 개발하지 않을까?**

많은 지질·지구화학 도해 템플릿을 모으고, 여러 지질 온도계/압력계 계산을 지원하며, 지구화학 계산과 현재 널리 쓰이는 기계 학습 기능까지 확장할 수 있는 도구입니다. 준비된 템플릿이 없으면 시각적 작도 도구로 만들고 공유할 수 있습니다. 현대적인 화면 설계와 다국어 지원을 더하면, 연구자는 하나의 소프트웨어 안에서 과학 작도와 계산의 기초 작업 대부분을 마칠 수 있습니다.

**GeoChemistry Nexus**는 이 흐름을 한곳으로 모으려 합니다. 시료 데이터 가져오기, 전처리와 보정에서 판별 도해 작성, 지온계 계산, CIPW 표준 광물 계산을 거쳐 PNG / SVG 등 형식의 내보내기까지, 가능한 한 같은 화면에서 끝냅니다. 동시에 **클라우드 템플릿 생태계**와 **커뮤니티 협업**을 통해 도해와 알고리즘이 계속 개선되고, 더 많은 연구자에게 빠르게 닿게 합니다.

## 처음의 개발 구상

마침 C#과 Python 등의 프로그래밍 언어에 익숙하고, 데스크톱 소프트웨어 개발 기술도 갖추고 있었습니다. 그래서 2024년 12월에 Demo 개발을 시작했습니다. 처음 기술을 고를 때 진지하게 생각했습니다. **어떤 언어와 구조가 이 목표를 가장 잘 이룰 수 있는가?**

첫 생각은 Python이었습니다. 프로토타입을 빨리 만들 수 있어 개발자에게는 유리합니다. 그러나 사용자 입장에서는 결정적인 약점이 있습니다. 첫째, 실행 효율이 낮습니다. 데이터 양이 적을 때는 영향이 크지 않아도 성능 차이는 남습니다. 둘째, 설치 패키지가 매우 커집니다. 예전에 WPF로 만든 간단한 프로그램을 Python으로 다시 작성한 적이 있습니다. 깨끗한 가상 환경에 패키징해도 결과물은 수백 MB였고, .NET으로 패키징한 프로그램은 십여 MB에 불과했습니다. 차이가 매우 큽니다. **단순한 기능을 위해 사용자에게 수백 MB에서 GB에 이르는 설치와 복잡한 설정을 감수하게 하는 것은 최선의 선택이 아닙니다**.

그다음으로 웹 개발을 고려했습니다. 장점은 분명합니다. 설치 없이 바로 열 수 있습니다. 그러나 서버를 오래 유지하는 높은 비용은 개인이 감당하기 어렵습니다. 그래서 결국 중심을 다시 클라이언트 개발로 돌렸습니다.

![plot_home_ui](/img/about-illustrations/03-technology-choice-path.png)

클라이언트 개발에는 여러 기술 방안이 있습니다. C++ 기반의 QT보다 .NET에 더 익숙합니다. .NET의 높은 실행 효율과 Windows의 보급을 함께 고려하여, 주요 개발 플랫폼으로 .NET을 선택했습니다. 처음에는 Avalonia로 Windows, Linux, macOS를 모두 지원하는 방안도 검토했습니다. 그러나 개발 중에 일부 프로젝트 의존성이 Avalonia와 호환되지 않아 이전 비용이 매우 높았습니다. 혼자서는 초기 단계에서 그 모듈들을 다시 구성하기 어렵습니다. 그래서 적어도 현재 단계의 작업은 Windows 플랫폼에 집중하며, 크로스 플랫폼 버전은 훗날 실현될 수 있습니다.
