# ℹ️ このソフトウェアについて

:::info

**「夢のスポーツカーが見つからなかったので、自分で一台造りました。」—— フェルディナント・ポルシェ**

:::

**GeoChemistry Nexus** は、私がとても長い期間にわたって保守していく最初のプロジェクトです。少なくとも今後 5 年間は、更新を続けるつもりです。

興味深いことに、最初の名前は **Geo-Thermometer** でした。はじめは、計算と作図をしやすい地質温度計の基本的なプログラムを作りたいだけでした。しかし開発が進み、とくに作図モジュールができたあと、もっと大きな目標を実現できると気づきました。そこで概念も機能も広がり、Geo-Thermometer から GeoChemistry Nexus へと発展しました。

## この名前にした理由

**GeoChemistry** は地球化学を表します。**Nexus** は、結節点、ハブ、交わる中心という意味です。

分散している地球化学の計算方法、データ処理ツール、鉱物化学分析、地質図解などを、一つのプラットフォームへまとめたいと考えています。

## GeoChemistry Nexus が必要な理由

地球化学と岩石学の研究では、**作図**と**計算**が別々のツールに分かれがちです。データの整理は表計算ソフト、ベースマップの描画は汎用のベクターツール、温圧計の計算は別のスクリプトや古いプログラム、という具合です。手順が分断され、形式がそろわず、再現のコストが高い。これは多くの研究者が日常的に感じている摩擦です。

一方で、よく使われる判別図、温圧計、関連する計算ツールの多くは、**長いあいだ更新が滞っています。** 新しく公表されたアルゴリズムや、古典的モデルの改訂をタイムリーに取り込むことが難しく、研究者は何年も止まったままの旧版を使い続けるしかないことがよくあります。より現実的な問題もあります。研究者が**自分で**新しいアルゴリズムや図解を開発しても、**手軽で開かれた公開の経路が不足している**ことが多く、成果は論文の付録、個人のスクリプト、狭い範囲での共有にとどまり、同じ分野へすばやく広がり、再利用されにくいのです。

![研究ツールの課題](/img/about-illustrations/02-research-tool-pain-points.png)

研究の中で、十分に厳密とはいえないやり方も見てきました。たとえば、地質図のベースマップを描くときに CorelDRAW で形を大まかになぞる、といったものです。見た目の差は大きくなくても、科学研究の立場から見ると、厳密な科学的精神に反します。

そこで考えました。**自分でツールを作ればよいのではないか。**

大量の地質・地球化学図のテンプレートをまとめ、さまざまな地質温度計・圧力計の計算に対応し、さらに地球化学計算や、いま広く使われている機械学習の機能まで広げられるツールです。用意されたテンプレートがなければ、視覚的な作図ツールで作成し、共有できます。現代的な画面設計と多言語対応を添え、研究者は一つのソフトウェアの中で、科学的な作図と計算の基礎的な作業の大部分を終えられます。

**GeoChemistry Nexus** は、この一連の流れを一か所に集めたいと考えています。試料データのインポート、前処理と補正から、判別図の作成、地質温度計の計算、CIPW ノルム計算、さらに PNG / SVG などの形式でのエクスポートまでを、できるだけ同じ画面の中で完結させます。同時に **クラウド上のテンプレート生態系** と **コミュニティによる協力の仕組み** を通じて、図解とアルゴリズムを継続的に改良し、より多くの研究者へすばやく届けることを目指します。

## 開発をはじめたときの考え

おりよく、私は C# や Python などのプログラミング言語に慣れており、デスクトップソフトウェアの開発技術も身につけていました。そこで 2024 年 12 月に Demo の開発を始めました。最初の技術選定では、真剣に考えました。**この目標を最もよく実現できる言語とアーキテクチャは何か。**

最初に思いついたのは Python です。すばやく試作できるので、開発者にとっては好都合です。しかし利用者の側から見ると、致命的な欠点があります。まず実行効率が低いことです。データ量が小さいときは影響は大きくありませんが、性能の差は残ります。次に、インストールパッケージが非常に大きくなります。かつて、最初は WPF で書いた簡単なプログラムを Python で作り直したことがあります。まっさらな仮想環境にパッケージしても完成品は数百 MB になり、.NET でパッケージしたプログラムは十数 MB でした。差は非常に大きいものです。**簡単な機能のために、数百 MB から GB 単位のインストールと複雑な設定をユーザーへ強いるのは、最善とはいえません。**

次に Web 開発を考えました。利点は明らかです。インストール不要で、開けばすぐ使えます。しかし問題は、サーバーを長く維持する高い費用が、個人の保守能力を超えることでした。そのため、最終的に重心をクライアント開発へ戻しました。

![技術選定の経緯](/img/about-illustrations/03-technology-choice-path.png)

クライアント開発には多くの技術的な選択肢があります。C++ ベースの QT と比べて、私は .NET の方が慣れていました。.NET の高い実行効率と Windows の普及を考え、主要な開発プラットフォームとして .NET を選びました。最初は Avalonia を使い、Windows、Linux、MacOS のクロスプラットフォーム対応も考えていました。しかし開発の過程で、一部のプロジェクト依存関係が Avalonia と互換せず、移行コストが非常に高いことが分かりました。個人の力で、初期段階からこれらのモジュールを作り直すのは困難です。そのため、少なくとも現段階では作業は Windows に集中しており、クロスプラットフォーム版は将来のどこかで実現するかもしれません。
